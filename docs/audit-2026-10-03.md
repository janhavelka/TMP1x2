# Pre-HIL audit, 2026-10-03

The driver exposes the documented TMP102/TMP112 register features. Two
configuration-trust defects were fixed, and hardware runners with standalone
host tests were added. This is software validation ahead of
the PCB: no board was flashed, no serial hardware session was opened and no
physical sensor result is claimed.

## Specification review

Re-read the archived register descriptions and checked the current TI documents:
[TMP102 SBOS397I](https://www.ti.com/lit/ds/symlink/tmp102.pdf),
[TMP112 SBOS473L](https://www.ti.com/lit/ds/symlink/tmp112.pdf),
[TMP102-Q1 SBOS702E](https://www.ti.com/lit/gpn/tmp102-q1), and
[TMP112-Q1/TMP112D-Q1 SLOS887H](https://www.ti.com/lit/ds/symlink/tmp112-q1.pdf).
The archive still matches these revisions. All 34 recorded SHA-256 entries
were verified; the archive and vendor licenses were left unchanged.

The [feature matrix](feature-coverage.md) covers all four registers, signed normal
and extended encodings, thresholds, conversion rates, shutdown/OS, thermostat
mode/polarity/fault queues, model/package addresses, physical GPIO access, general
call and Alert Response. No additional writable chip feature was found missing.
HS master-code sequencing, bus frequency and line-timeout testing remain transport
responsibilities. A faster I2C clock alone does not implement high-speed mode.
There is no chip identity register or continuous-mode sample sequence counter.

TI specifies that register bytes can take effect individually. Existing tests
modeled failed writes as either rejected or fully accepted; the expanded tests
also accept only the MSB, including possible OS/SD changes without changing EM.
Tests cover both format directions, threshold replay, and a conversion that never
sets OS ready. Elapsed time alone never authorizes a fresh measurement.

## Confirmed defects and corrections

| Finding | Consequence | Correction / regression |
| --- | --- | --- |
| Tracked word diagnostics ignored observed CONFIG/TEMP format differences. | An external EM transition observed through `readRegister` and reversed before recovery could lose format evidence, accepting a half/double-temperature payload. Threshold and invalid fixed-bit observations were also ignored. | Successful word reads retain their diagnostic output but latch dirty/format evidence. Raw reads still bypass observation/health. Tests cover all registers, both formats, invalid bits, failure output preservation, health and cache separation, and recovery after CONFIG returns to the desired setting. |
| `verifyConfiguration` compared TLOW only after reading THIGH. | A failed THIGH callback replaced an already observed TLOW mismatch with a transport error as the only dirty-state explanation. | Latch TLOW mismatch immediately; return the later transport error while retaining the earlier trust cause and its raw word. Both formats are tested. |
| HIL instructions suggested physical testing above 128 C. | Catalog operating specifications stop at 125 C; extended encoding does not expand them. | Use synthetic register/count tests for extended-only values; physical thermal tests stay within the exact part's ratings. |
| Firmware examples always initialized the default model/address before CLI retargeting. | On a shared board, startup could address another peripheral instead of the intended TMP sensor. | Shared build-time `TMP1X2_MODEL` / `TMP1X2_I2C_ADDRESS` settings are applied before startup initialization in both adapters; invalid address/model/ALERT combinations fail compilation. |

Both new defect regressions were compiled against copies of their original HEAD
source and failed at the expected dirty-evidence assertions. They pass with the
corrected implementation. Synchronous and owner configuration still share their
existing state machine; no hidden retry, bus ownership, allocation or platform
dependency was introduced.

## Framework and application boundary

The driver is independently usable standard C++17. Its public headers and
implementation require no application repository, Arduino, ESP-IDF or RTOS.
The core does not allocate memory, own the bus, configure GPIOs or create tasks.
Synchronous calls suit simple loops; cooperative operations optionally bound
each turn's transport work. Both use the same chip configuration engine.

Arduino-ESP32 and native ESP-IDF have separate example adapters and share the
framework-neutral diagnostic CLI. All pin assignments and transport setup stay
in those adapters. The native tests and isolated release-package consumer build
without either SDK or any neighboring repository.

The [integration contract](integration.md) and [operation contract](owner-operations.md)
describe callback lifetime, physical health, relative deadlines, cancellation
and sample freshness in application-neutral terms. Model, address straps and
optional ALERT routing belong to each application's BOM and board configuration.

## HIL preparation and remaining gates

[Runner instructions](hil-runner.md) describe smoke, configuration, one-shot,
stress, comparator ALERT and guided disconnect/reconnect suites for the shared
Arduino/native IDF CLI. The runner requires an explicit port/model/address,
checks terminal responses and samples, records JSON plus a transcript, and
attempts verified restoration after mutating tests. It never flashes firmware
or silently issues a shared-bus reset. Tests exercise fragmented/failed responses
and the actual compiled CLI with a simulated sensor; that is not HIL execution.

The [hardware checklist](hardware-validation.md) still owns physical qualification:
address straps, pull-ups and voltage, real conversion/EM timing, negative
temperatures and accuracy against a reference, interrupt-latch acknowledgement,
exact fault-queue timing, shared-bus behavior, and signal/current measurements.
An automated suite pass proves only its selected checks on the recorded fixture.
