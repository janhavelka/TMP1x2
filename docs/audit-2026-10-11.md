# Maintainability audit, 2026-10-11

Reviewed the core, cooperative jobs, shared CLI, framework adapters, native
tests, build tooling and integration documentation. The starting checkout was
`b4c624e`, clean and synchronized with `origin/main`. No public method, command,
supported model or framework was removed. Physical hardware remains untested.

## Completed cleanup

| CONFIG fixed-bit checks, stable-bit comparisons and dirty-state recording were repeated in diagnostics, verification, replay and one-shots. | One private helper keeps these checks consistent, retaining each caller's diagnostic text and transport sequence. |

The owner scheduling regression checks clock-hook and caller-time operation,
post-callback wait anchoring, zero transfers before the conversion wait expires,
poll hints, successful fresh samples, and 32-bit clock wrap. Existing fault tests
cover both EM directions, partial writes, cancellation, health accounting and
output preservation. Existing CLI/HIL tests cover the shared sampling path.

## Complexity retained deliberately

Health, configuration trust, pending format refresh and sample provenance carry
different evidence. Combining them would lose information after partial writes,
external changes or failed reads. The EM state machine retains its old-format
settle and completed new-format conversion requirements. Synchronous and owner
operations continue to share that engine.

Recovery's preliminary CONFIG read resembles the apply engine's observation,
but removing it changes when failure invalidates trust and which format changes
are observed. It remains. Public compatibility aliases also remain: absence of
an internal call is not evidence that downstream applications do not use them.

The independent register models test different fault behavior. They remain
separate rather than sharing the driver's own codec or one large configurable
mock. The CLI's desired profile, sample and result caches retain session history
that differs from the driver's state. Framework adapters and shared-bus helpers
already have narrow responsibilities; no additional abstraction was justified.

## FieldCore-node integration fit

Read the neighboring FieldCore-node checkout at `fb38bed1` without changing it.
Its `docs/guidelines/rodtester.md` and `docs/guidelines/rodtester/integration.md`
describe preparation for four detachable heads containing TMP112 sensors behind
a TCA9548A. The connector has no ALERT conductor. There is no TMP1x2 runtime
module or dependency in that checkout yet, so this is an interface review, not
a completed application integration.

The existing library supports the planned owner model: one permanent instance
per head, synchronous callbacks, bounded polls, retained operation tokens and
bus-silent wait hints. The application still needs to implement and test:

- Route selection and verification as separate owner phases, with route and
  address identifying the sensor and the route re-established on continuation.
- Fair scheduling of retained jobs while other sensors convert, without
  cancelling/resubmitting them to free the active slot.
- An adapter for `include/TunnelMonitor/i2c/I2cOwnerTransport.h` that checks byte
  counts before returning OK, preserves transport error detail, and keeps each
  callback within the original owner deadline. The transport's write-effect
  evidence can remain in application diagnostics; the driver conservatively
  retains uncertainty after a failed write attempt.
- Mapping low 32 bits of owner time to the driver's clock, bounding relative
  operation budgets, and translating poll hints back through relative delays.
- Explicit BOM model selection, fresh one-shot acquisition where required, and
  cancellation/result consumption before invalidation and recovery on replacement.

The reusable rules are now in [owner operations](owner-operations.md). Routing,
RTOS ownership, 64-bit deadlines and head identity stay in the application; the
core still builds without any FieldCore-node or framework dependency.
